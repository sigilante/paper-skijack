\begin{abstract}
We present SKIjack, a language for writing metacircular
interpreters over the $SKI$ calculus, whose feature set is designed off
an existing artifact rather than designed: the 618-atom 
self-interpreter of \citet{Davis2027}, decomposed into its fuel loop, 
its dispatch, its spine walker and its atoms, with each part promoted 
to a surface construct.  
Over a homoiconic calculus the designer chooses where quotation happens.
Over a calculus without self-quotation this choice is unavailable: no
combinator can take another apart, so reification is metalevel by
theorem and a language's staging boundary is fixed.
Declaring an object language generates that 
furniture, so authoring the semantics of a new symbol---the core 
operation performed by hand in the previous paper---becomes merely a 
two-line  edit.  Quotation is available at compile time only, and at the
positions where a function would be asked to behave as data the checker
statically refuses every occupant it can prove to be one.  A bound 
namespace is a language feature: a path is written as a literal of a 
declared path type and compared by structural equality on its encoding, 
and a blocked run is replayed under a namespace that only ever grows.
\end{abstract}

\section{Introduction}\label{sec:intro}

Over a homoiconic calculus (Lisp, Nock) the metacircular tradition
\citep{McCarthy1960,Nock4K} gets 
quotation for free and the language designer chooses where evaluation 
stages live. Over a non-homoiconic calculus no such choice is possible: 
Proposition 3.1 of \citet{Davis2027}, which follows from Theorem 3.2
of \citet{JayGivenWilson2011}, demonstrates that no closed term quotes
\emph{every} live term, so the compile-time/runtime 
line is fixed prior to the language's design;
the two operations the calculus cannot do for itself, quote and 
recognize, must go to the compiler and the virtual machine 
respectively.  \citet{Davis2027} presented a metacircular evaluator for 
$SKI$ which is written and evaluated in the same combinator system.  
This capacity 
immediately suggests the construction of a battery of computational 
conveniences and abstractions within the same system; to wit, a 
language.  We present SKIjack (pronounced ``skyjack''), a 
closed-supercombinator macro-like language built in and targeting the 
non-homoiconic $SKI$ calculus as its  instruction set architecture.  
Every named entity compiles to a closed term and every name is resolved 
before anything runs, so the language has no runtime environment to 
address: bracket abstraction has already closed what a subject-oriented 
calculus would have to carry.  SKIjack is evaluable on any $SKI$ 
interpreter as a virtual machine.

% The asymmetry that forces the staging line is older than either
% calculus's programming languages, and naming it early makes the rest of
% the design read as consequence rather than taste.  \citet{Bohm1968}
% proved that two distinct $\beta\eta$-normal forms can always be told
% apart from the outside: some context applies them to arguments and
% recovers any two results we please.\footnote{Stated for the
% $\lambda$-calculus and for $\beta\eta$-distinct normal forms; see also
% \citet[\S10.4]{Barendregt1984}.  The probes this paper uses run on
% Scott-encoded data under weak reduction, which is not that setting, so
% we cite separability for the asymmetry it names and not as a
% completeness result for the method.}  \citet{JayGivenWilson2011} proved
% that no combinator can take another apart from the inside.  Both papers
% of this pair live in the gap between those two results.  Reading a
% compiled term by applying it to fresh markers and seeing which one comes
% back is the outside; Proposition 3.1 is the inside; and a VM jet is
% permitted to factorise a live term precisely because it is the Turing
% machine with the term on its tape, which is to say outside as well.
% Quotation goes to the compiler and recognition to the VM not
% because that is convenient but because those are the only places the
% operations exist.

The \texttt{whnfF} metacircular interpreter and \texttt{UQ} unquoter 
function presented in \citet{Davis2027} are the starting point for our 
work.  That paper discussed extensions to the $SKI$ calculus built on
higher layers of interpreters, introducing an \texttt{Err} error type,
a \texttt{Maybe} partiality type, and discussed implications such as
namespace value retrieval and other innovations.  By authoring a new
symbol at one site, the \texttt{whnfF} approach enables extension and 
modification of the combinator's semantics, permitting it to behave more
like a language than a mere combinator system.  This paper presents
such a language, SKIjack, and three contributions for $SKI$ combinator
research.  First, object-language declarations that generate an
interpreter's furniture---constructors, case, spine walker,
rebuilder, default step equations and fuel loop---so that authoring a
semantics at one site is a declaration rather than a term construction,
and costs nothing over the hand construction: six programs compile to
the artifacts of \citet{Davis2027} atom for atom.  Second, a two-level
execution model in which a quotation is run under a named interpreter
with an explicit fuel budget, so that a program's steps, divergence and
errors are observable because the interpreter is an ordinary term the
program names.  Third, a namespace as a language feature: a resolver is
a core parameter, paths are restricted to literals of a declared path
type and compared structurally, and the namespace literal compiles to a
resolver.

\section{Background}\label{sec:background}

The calculus is the usual one.  Terms are built from $S$,
$K$ and $I$ by application alone, written
left-associatively, with the rules $I\,x \to x$, $K\,x\,y \to x$ and
$S\,f\,g\,x \to f\,x\,(g\,x)$.  There are no variables and so no
binding, no substitution and no environment; a surface language with
binders reaches this calculus by bracket abstraction, which is the whole
of the compiler's back end \citep{Turner1979b}.

Data are Scott-encoded.  A datum of an $n$-constructor type is a function
of $n$ continuations that applies the one belonging to its own
constructor to its own fields, so a value \emph{is} its own case
analysis and there is no separate eliminator
\citep{Scott1962,Jansen2013,BohmBerarducci1985}.  The order of the
continuations is the order of the declaration, and it is part of the
interface rather than a convention: a wrong continuation order is not a
type error but silently different behaviour, which is why
\S\ref{sec:boundary} treats case completeness and order as the first
thing a checker owes an author.

The artifact this paper compiles to was built by \citet{Davis2027}: a
fueled normal-order interpreter for $SKI$, written in $SKI$, 618 atoms,
with an unquoter \texttt{UQ} at 43 and structural equality on encoded
terms at 240.  Fuel is a Scott numeral and its semantics is exact---a
budget of $k$ permits $k$ step-attempts, the last of which must be the
no-redex check---so a run that performs $s$ contractions needs $s+1$.
That paper reports the interpreter running a one-step object reduction
in 340 host contractions, running the unquoter's output in 91,556, and
running \emph{itself} in 504,930; it also proves the proposition this
paper's design is organized around, that no closed term quotes every live
term.  We reproduce those counts and do not re-derive them.

Four rulers get used on one object and are worth separating now, since a
reader who confuses them will think the paper contradicts itself.  The
interpreter is 618 \emph{atoms}; as a tree that is 1{,}235 \emph{nodes};
sharing brings the graph to 348 \emph{distinct nodes}, counted by identity
 as the term is built (by structure it is 147); and printing it
in the notation used here takes 2{,}109 \emph{characters}.  Atoms are
the unit for every claim below, and the others appear only where they
are named.

\section{Lineage}\label{sec:lineage}

SKIjack is a language entirely based on the $SKI$ combinator calculus,
and in particular on improving the expressiveness of $SKI$ reasoning by
the introduction of a standard machinery in the form of generated
supercombinators.  We survey the historical and technical lineage of
pure combinator computation that informs SKIjack's design.  SKIjack is 
far from the first language or machine concept to lean into
pure combinator computing.  The present paper leans on five classic 
results from Corrado B\"ohm's work:
\begin{enumerate}[nosep]
  \item  \emph{CUCH}.  \citet{BohmGross1966} introduced the CUCH 
  (CUrry-CHurch), a surface for writing programs whose meaning is given 
  by combinators.  The $SKI$ calculus (including SKIjack) operates 
  under a more severe constraint:  while CUCH's designers were able to 
  place its affordances such as quotation wherever they pleased, pure 
  $SKI$ calculus cannot quote expressions (Proposition~3.1 of
  \citet{Davis2027}).
  \item  \emph{Separability}.  \citet{Bohm1968} proved that if two 
  closed $\lambda$-terms are $\beta\eta$-normal and $\beta\eta$-distinct 
  then for any two terms $P$ and $Q$ chosen in advance there are 
  arguments sending the first to $P$ and the second to $Q$.  What we 
  take from this is directional and nothing more: structure is 
  available from outside a term and not from within it.  It does not 
  transfer to our setting term for term, and the counterexample is the 
  one \citet{Davis2027} uses to motivate Proposition 3.1---$S\,K\,K$ 
  and $I$ are distinct normal forms of weak combinatory logic that 
  agree on every argument, so no applicative context separates them.  
  What licenses the practice of this paper is therefore not Böhm's 
  theorem but the metalevel: a host may read a term's syntax.  Our 
  fresh-marker probes are a behavioural check and not a decision 
  procedure for term identity, which we settle by structural hash.
  \item  \emph{Term-algebra schema}.  A type declaration generates its 
  constructors and its case form by the schema
  \citet{BohmBerarducci1985} gave for term algebras, in the Scott 
  variant \citep{Scott1962,Jansen2013} rather than the Church one:  an 
  interpreter's step function wants case analysis in place of a fold 
  which fixes the declaration order as the continuation order.
  \item  \emph{First self-compiling compiler}.  The first compiler 
  written in its own language is recognized as \citet{Bohm1954}, his 
  1951 dissertation at ETH Z\"urich \citep{KnuthPardo1980}.  In the 
  case of SKIjack, the compiler carries out quotation at compile time.
  \item  \emph{Self-interpreter with a normal form}.  Finally,
  \citet{BerarducciBohm1993} gave a self-interpreter of the 
  $\lambda$-calculus having a normal form.  
\end{enumerate}

Bracket abstraction permits the procedural compilation of a low-level 
applicative language to combinators \citep{Turner1979}; there is a 
related abstraction algorithm \citep{Turner1979b}.  That technique was 
realized in hardware as the ``$SKI$ Machine'' (SKIM), a 
graph-reduction machine built on a fixed ``Turner set'' of combinators 
\citep{ClarkeEtAl1980}, and in its successor 
\citep{StoyeClarkeNorman1984,Stoye1985}.  \citet{Hughes1982} then 
introduced the supercombinator---the closed abstraction compiled as 
one unit---expressly as the alternative to a fixed set, whose 
expansions grow with the program; the compiled-graph-reduction line 
that followed runs through the G-machine \citep{Johnsson1984}.  Our 
own position is the awkward one of taking both: we lift as Hughes does 
and then abstract each supercombinator into $\{S,K,I\}$, re-incurring 
the growth he set out to avoid, and pay down this debt with the virtual 
machine semantics of \S\ref{sec:runtime}.  (A standard account of the 
whole pipeline has been given by \citet{PeytonJones1987}.)  The SKIM 
tradition operated with a fixed set of recognized combinators executed 
natively in microcode, an accelerated process comparable to the ``jet''
approach we will adopt in this work.  Much of this work was concerned
with the cost of any particular abstraction, in combinators per source 
symbol \citep{Noshita1985,JoyRaywardSmithBurton1985}, and we report atom
counts in line with that tradition.

In the preceding research program, the interpreter lived either in a 
machine (Turner) or in microcode (SKIM), with the reduction engine as 
an external given.
The object introduced by \citet{Davis2027} is a 618-atom 
self-interpreter which exists as a term within the language it 
interprets.  Previous supercombinator work has had no reason to write
such an artifact; its self-application question was the compiler
bootstrapping in its own source language, not the reducer reducing
itself, and so the tower, the per-level cost, and the encoding boundary
never arose there.

However, pursuant to the introduction of a self-interpreter as a term 
within the language, new considerations arise.  Staging becomes a design 
problem: Turner's SASL could not quote either, but because no SASL 
program was trying to run another SASL program under a fuel budget, 
there was no obligation to address the lack.  Declaring an object 
language becomes a language feature, since an interpreter's  
constructors, case form, spine walker, rebuilder and fuel loop can be 
generated from the declaration rather than written.  Finally, the native 
compiler owes its output a strict discipline:  expansion is bijective, 
terms lift back to named source, and the dictionary is published and 
keyed by structural hash.  This discipline becomes crucial because the 
emitted term is simultaneously the object of study and the key a VM 
matches on, whereas nobody expected to read the output of a SASL  
compiler.

This last merits an aside.  A virtual machine 
(\S\ref{sec:runtime}) may identify supercombinators of arbitrary size
and reduce them against a table of known outcomes in native code (what
we call a ``jet'', short for ``jet-accelerated code'', a term from the 
Nock computing lineage).  Mechanically, such a procedure
corresponds to Turner's extended combinator set and SKIM's microcode.  
However, our theorem does not licence arbitrary native code replacement;
the interpreter jet performs a structural recognition that no
term can perform for itself and thus is not an optimization of an
operation the language has.  The operational consequence of this
prohibits a jet from quoting on behalf of a running term.  The
VM is addressed briefly in \S\ref{sec:runtime}.

\section{The interpreter}\label{sec:interpreter}

The \texttt{whnfF} function forms the centerpiece of the interpreter, 
responsible for reducing terms to weak head normal form.  It
orchestrates the evaluation strategy for the language, ensuring that 
terms are reduced correctly according to the operational semantics.
It also suggests the language features that are necessary to support 
such an evaluation strategy, which will emerge in SKIjack as primitives.
There is also an unquoter function \texttt{UQ}, responsible for 
converting weak head normal forms back into their original syntactic 
representation.  This is necessary for maintaining the correspondence 
between the evaluated terms and their original syntactic forms, ensuring 
that the interpreter's output can be related back to the source code.
In \citet{Davis2027}, we simply named the features by their operational
significance as a shorthand; here they become language elements in their
own right.

Table~\ref{tab:atoms} gives some typed forms with their defining 
equations and with closed $\{S,K,I\}$ terms emitted by the expander
(i.e., compiled output).  Three of the six reduce to
the same term, and two more are a second same term.  This results because
a Scott datum is its own case analysis, so the first constructor of any 
two-constructor type discards the remaining continuation and is $K$, 
whatever the type was called, and a one-field second constructor applies 
one continuation to one field and is the same eight atoms whether the 
field is a numeral or a term.  At the level of terms the type 
distinctions are erased.  SKIjack maintains the type discipline at
compile time (\S\ref{sec:boundary}).  A checker may reject a
program that offers a numeral where a list is wanted, but nothing
downstream of the expander could tell the two apart, because downstream
of the expander they are one object.  (It is also why the dictionary that
names these expansions is keyed by the hash of a term and not by a name.)

\section{The language}\label{sec:language}

The \texttt{whnfF} function of \citet{Davis2027} introduced a number of
independent operational terms within its full expression, and these
suggest language features such as its loop, its comparison and dispatch,
and its atoms (\texttt{suc}, \texttt{zero}, \texttt{nil}, \texttt{just},
etc.).  These features were composed into larger machine terms, which
are similar to the supercombinators of \citet{Hughes1982}.

SKIjack's features are written as a set of object terms in the 
metacircular evaluator; in essence, it is a macro language with a gently 
typed surface discipline.  They name and highlight the components of
\texttt{whnfF} and other recurrent supercombinators, augmented with
affordances to make the language expressive and composable.

A language description of SKIjack is provided in Appendix~\ref{sec:language-description}.

\subsection{Design principles}\label{sec:design-principles}

Since quotation of live terms is not supported, the language relies on 
the macro-like composition of its object terms rather than runtime 
evaluation.  A hard line between runtime quotation and compile-time
quotation is forced by Proposition~3.1 of \citet{Davis2027}, which follows from Theorem~3.2 of \citet{JayGivenWilson2011}:  ``No closed term $Q$ over $\{S,K,I\}$ satisfies $Q\,M \twoheadrightarrow \langle M\rangle$ for every closed $M$.''  Everything on the encoded side of 
that line is closed under the calculus, including running encoded terms, 
comparing them, and building cores.  Everything that would turn a live 
value back into data is unavailable and must be staged via the virtual
machine.  One design problem is to make that line visible and 
comfortable.  Another difference from traditional macro languages is 
that weak SKI reduction is call-by-name: arguments are never forced 
early, \texttt{K I Ω} is \texttt{I}, and no form needs thunking.

The basic components of SKIjack are thus:  a macro layer; Scott encoding;
recursion through $Y$; interpreters, the unquoter, and equality on
encoded terms like paths; the behavioral verification discipline; and
the existence of a runtime which can jet the compiled code for more
efficient execution.

A SKIjack program consists of a series of declarations and definitions that establish the structure and behavior of the object language terms.  These programs may rely on a prelude to provide essential cores and utilities.  Listing~\ref{lst:ascii} shows a simple example of

\subsection{Representation ABI}\label{sec:representation-abi}

A handful of representation choices sit between the compiler and
everything written in the language.  We call this the representation 
ABI because it specifies the contract between separately produced 
compiled artifacts, not because there are bytes or linkers.  A term 
emitted by this compiler must interoperate with terms built by hand, 
and with native code that recognizes them; the two would fail to 
compose if either disagreed about the order of continuations.  In a 
Scott encoding that order is simultaneously the layout of a datum and 
the convention for calling it.

A cell \texttt{[a b]} is the Scott 
pair $\lambda c.\,c\,a\,b$, whose only operation is to hand its 
components to a selector; the head is \texttt{p K} and the tail
\texttt{p (K I)}.  Axis addressing follows a binary tree numbering, 
with axis 1 being the whole, axis $2n$ the head of axis $n$ and $2n+1$ 
its tail, and an axis compiles to the corresponding chain of 
projections at one projection per bit.  Axes only validly address
cells; a term's application tree is code, which by Proposition 3.1
cannot be inspected by any term \citep[Thm.~3.2]{JayGivenWilson2011}, and so the notation that reaches into 
data stops at that boundary.

A type declaration is an ordered constructor list, with the order 
specified in the ABI.  The declaration generates each constructor as 
$\lambda \mathit{fields}.\,\lambda c_1\ldots c_n.\,c_i\,\mathit{fields}$
as well as the case form to apply a datum to $n$ continuations in 
declaration order, per the schema of \citet{BohmBerarducci1985} in its 
Scott rather than Church variant. Booleans are \texttt{K} for yes and 
\texttt{K I} for no, so a conditional is application to two 
continuations.  Numerals are Scott numerals and serve as fuel; there is 
no native integer, and arithmetic is unary.

\subsection{Kernel forms}\label{sec:kernel-forms}

The kernel contains about a dozen forms and is intended to remain fixed.
Each form has exactly one expansion, given by a fold over the
syntax tree: a name resolves in the compile-time table to a binder, a
sibling equation, a constructor or a macro; juxtaposition denotes 
application; a cell is a pair; an axis pick is a projection chain; a 
lambda and an equation are bracket abstraction over their binders; a 
case applies a datum to one continuation per constructor in declaration 
order; a quotation is a Scott encoding computed at compile time; a 
macro is expanded at its use site; and the two evaluation forms hand a 
quotation to an interpreter.  Everything else is composed of these 
primitives.

Because every rule is a fold, the expander has no semantics of its own: 
the same source gives the same closed term, atom for atom, 
deterministically and context-free.  The surface grows in macros and in 
the library rather than in the compiler.

\subsection{Supercombinators vs.\ macros}\label{sec:supercombinators-vs-macros}

A supercombinator and a macro can look alike in source code but are not
equivalent.  An equation is lambda-lifted over its binders and over the 
sibling equations it calls, tied with $Y$ where it recurses, and 
emitted once as a supercombinator.  A supercombinator is a closed term 
forming a single node in the graph and shared by every use.  In 
contrast, a macro has no runtime existence but is expanded into each 
use site, so it costs nothing to reach and is duplicated per use.  
Small things (derived combinators, booleans, projections) tend to be 
macros, while large things (an interpreter, equality on encoded data, 
the standard library) prefer to be supercombinators.  (Hughes proposed 
supercombinators as the alternative to compiling into a fixed 
combinator set, whose expansions blow up in size; here the fixed set is 
the non-negotiable instruction set, so each lifted definition is 
abstracted into $\{S,K,I\}$ after lifting.)

The structural consequence is more important than the cost.  Compilation
leaves the supercombinators intact and nested inside one another:  in 
the compiled interpreter of \S\ref{sec:interpreter}, \texttt{sp} is a 
subterm of \texttt{step}, \texttt{step} of \texttt{whnfF}, \texttt{rb} 
of \texttt{stepS}, and 40 of the term's 348 distinct nodes are entries 
of the program's own dictionary.  This makes a supercombinator 
liftable back to its name, and lets a runtime recognize it
(\S\ref{sec:runtime}); a large open term offers neither improvement.  
Macros are hygienic by default, since a capture is invisible in source 
and shows up only as a body silently reading the wrong binding; a 
marked capturing form is reserved for the cases that want it.

\subsection{The standard subject}\label{sec:standard-subject}

A language of this shape wants a library, and the library wants to
arrive as data rather than as a compiler built-in.  We call this a
subject in the tradition of subject-oriented programming.  The
virtual machine applies a loaded program to one argument, the
\emph{subject}, which carries the library at fixed axes---the
primitives and $Y$, pairs and projections, Scott lists and numerals, 
equality on encoded terms, the unquoter, and the interpreters
themselves as ordinary supercombinators.  (A subject is not the same as
an environment: names are resolved in a compile-time table and are gone 
before anything runs, and no compiled program applies itself to the 
subject to find its own names.)

% This is the one component of the design that is specified and not
% built.  Until it exists, a library name is inlined as its expanded term
% at each use, exactly as the artifact of \citet{Davis2027} writes its
% encodings out by hand, and a name used twice in one quotation is
% duplicated rather than shared.  The atom counts reported in this paper
% are therefore upper bounds in a specific and uninteresting way: a shared
% subject would lower them without changing a single reduction.

\subsection{The quotation line}\label{sec:quotation-line}

So far, SKIjack is a fairly ordinary supercombinator language.  The
line that separates it from SASL or SKIM is where a term may be turned
into data given that quotation is only available at compile time.
The form \texttt{<t>} emits the Scott encoding of \texttt{t}
against the enclosing program's object type, computed by the expander;
inside the brackets a name is a constructor of that type if it is one
and is otherwise inlined and encoded in place.  There is no form, and
\emph{there can be no form}, that takes an arbitrary live value and yields its 
code.  Even if the base representation is always $\{S,K,I\}$, SKIjack
and the \texttt{whnfF} interpreter are not truly homoiconic, as code
can never cross back over into data.

SKIjack thus makes this refusal explicit and visible rather than 
silent through its modest type system.  Equality is offered on encoded 
data and refused on functions; a namespace key is a value of a declared 
path type and not an arbitrary term; a quotation's argument is
source and not an expression to be evaluated first.  Each of those
would require a function to behave as data, so the
checker rejects a program that puts one there before the expander is
reached (\S\ref{sec:boundary}).

\section{Execution model}\label{sec:execution-model}

A declaration runs at one of two levels:
\begin{itemize}[nosep]
  \item  \emph{Level 0}: the compiled term is handed to a reducer as it 
  stands.  This is ordinary evaluation: weak reduction is call-by-name, 
  arguments are never forced early, and no form needs thunking.  
  Nothing blocks and nothing can be observed partway; a term either 
  reaches weak head normal form or it does not.
  \item  \emph{Level 1}: a quotation is handed to an interpreter 
  together with a fuel budget, written \texttt{<t>@n}, or \texttt{I |- 
  <t>@n} to name an interpreter other than the default.  This compiles 
  to an application: the interpreter, its parameters, the Scott 
  numeral, and the quoted program, as the lifted form in
  \S\ref{sec:language} shows.  Fuel must be explicit because a budget 
  of $k$ permits $k$ step-attempts, of which the last must be the 
  no-redex check, so a computation of $s$ contractions needs $s+1$. The 
  budget cannot be inferred by the compiler, since a term's running 
  time is its running time and convergence is only semi-decidable.  
  Elided fuel, written \texttt{@[]}, is therefore a \emph{runtime 
  policy} rather than a compile-time value: the budget doubles from a 
  small start until the program produces something other than a timeout 
  or a configured ceiling is reached, and the ceiling is reported as a 
  timeout rather than hidden. (The one case a compiler could fill in is 
  a term it can prove affine, and that case is not interesting enough 
  to special-case.)
\end{itemize}

The levels differ in what is observable.  At level 1, a program's steps
are counted, its divergence is bounded, its errors are values, and its
scry operation can block.  All of these are available because the
interpreter is itself an ordinary term the program may name.
Virtualization is not cheap, in any case:  \citet{Davis2027} measured
the base interpreter at 340 host contractions for a single object step.

\section{Interpreters as declarations}\label{sec:interpreters}

The central move of \citet{Davis2027} was to author the semantics of a 
new symbol at one site of an interpreter. It performed that move by 
hand, in a definitional layer with no surface language above it. With 
SKIjack, this becomes simply a declaration. Before extending the 
interpreter, though, we reproduce it: Listing~\ref{lst:whnfF} defines 
\texttt{whnfF} in SKIjack and it compiles atom for atom to the term 
printed in Appendix~B of \citet{Davis2027}.

\begin{lstlisting}[float=htb,
                   label=lst:whnfF,
                   caption={The \texttt{whnfF} function defined in 
                   SKIjack.  Pleasingly, this program produces the 
                   identical $SKI$ artifact as Appendix B of

term === S | K | I | App term term
maybe === Nothing | Just term

  step m = sp m nil stepS stepK stepI
  loop1 f m n2 = step m (Just m) (f n2)
  loop n m = n Nothing (loop1 loop m)
}
resS acc c0 c1 c2 = c0 acc
resK acc c0 c1 c2 = c1 acc

sp m acc = m (resS acc) (resK acc) (resI acc) (spApp sp acc)

stepI1 x rest = Just (rb x rest)

A type declaration names an object language, and from it the compiler
generates what an interpreter over that language needs: the
constructors and the case form, the spine walker that decomposes an
application into a head and an argument list, the rebuilder that puts
one back together, a default step equation for each leaf of the object 
type, and the fuel loop, whose shape is read off the outcome and result types. The timeout constructor is the last terminal of the result type,
which for \texttt{maybe} is \texttt{Nothing}.

The original paper's observability pair here reduces to two interpreters
over a five-constructor object language, differing at the single
equation that handles the new leaf.  The whole program is seven lines:

\begin{lstlisting}[label=lst:t3,float=tb,
                   caption={Two interpreters over a five-constructor
                   object language, differing in one equation.}]
term5   === S | K | I | App term5 term5 | Err
outcome === Stepped term5 | Done | Errd
result  === RVal term5 | RErr | RTime

omega = S I I (S I I)

wf5Abs := { stepErr acc = Errd }
wf5Omg := { stepErr acc = omega }
\end{lstlisting}

\noindent The first absorbs the new symbol into an error outcome; the
second diverges on it.  They compile to 768 and 771 atoms, again
matching the artifacts of \citet{Davis2027} atom for atom, and they
reproduce that paper's observability table.

The edit is as surgical as the claim requires, and the compiler makes
that checkable rather than rhetorical.  The two cores differ in one
equation, and the compiled terms differ by exactly what that equation
costs: \texttt{stepErr} is 4 atoms in the first core and 7 in the
second, and 768 and 771 differ by precisely those 3.  The difference
propagates outward unchanged---\texttt{step} is 684 against 687 and
\texttt{loop1} 736 against 739---so nothing else in either
interpreter moved.  All the rest, some seven hundred atoms of spine
walker, rebuilder, four default step equations and fuel loop, is
generated from the three type declarations above them, and generated
identically for both.  For $SKI$ constructions of this shape the
compiler is on par with hand construction, at no cost in term size.

\section{The namespace}\label{sec:namespace}

The artifact of \citet{Davis2027} accepts any term as a ``scry path'',
or fixed address to value mapping.  The language does not inherit that
permissiveness, instead restricting valid scry paths to the
\texttt{path} type, a list of tagged segments,
\texttt{path === Nil | Cons seg path}, and refusing on anything else.  
This is not merely tidiness:  paths are compared, and comparison is 
only available on encoded data.  An arbitrary term as a key would be a 
function in a position that requires a datum, which is forbidden 
(\S\ref{sec:boundary}).

The resolver is a parameter of the interpreter core rather than a term
closed over inside it.  This makes a namespace a namespace: the
core is written once, and supplying a different resolver does not
recompile it.  A namespace literal is sugar for building one.  It
expands to a chain that compares the incoming path against each key
with \texttt{EQ5} over the encodings, answering with the oracle's
found-constructor at the first match and its not-yet-constructor when
nothing matches, and the chain is an ordinary closed term like any
other.  Listing~\ref{lst:ascii} and Table~\ref{tab:lookup} show that
arrangement as compiled and run.

How the namespace handles a negative answer is
\citet{Davis2027}'s, and we restate it here because what is new in this
paper sits on top of it: that the resolver is a core parameter rather
than a term closed over inside the interpreter, and that a namespace
literal compiles to one.  The interpreter's outcome and 
result types each carry an extra constructor that holds the path that 
blocked, and the driver, meeting one, records the fact and re-runs the 
program from the top under a resolver that now knows it.  While 
re-running looks wasteful, it is the guarantor of the soundness.  
Because the namespace is append-only, a fact once learned is never 
withdrawn, so a later run can only get at least as far as an earlier 
one; the blocked run is not resumed in the middle, where the 
intermediate state would have to be trusted, but discarded and replayed 
against more knowledge.  We thus require the namespace to be fixed and
referentially transparent; if a fact can change, replay proves 
nothing.  Furthermore, fuel is not neutral across a resumption.  A
replayed run spends its budget again from the beginning, so the fuel a
program needs is a function of how many times it blocked, and a budget
that sufficed on the first attempt may not suffice on the third.

\subsection{A character table}\label{sec:chars}

The smallest useful namespace that is not a toy is a character table:
the stage of a parser that maps a source character to the term it
denotes.  It is worth separating because it is the one part of parsing
that is a lookup rather than a decomposition, and so the one part that
a calculus which cannot take terms apart can still do.  Declaring the
segment type and the facts is the whole of it; the interpreter is the
\texttt{wfN} of \S\ref{sec:interpreters}, unchanged and uncompiled
again.

\begin{lstlisting}[label=lst:chars,float=tb,
                   caption={A character table as a namespace, and four
                   programs that read from it.}]
seg === Src | Ess | Kay | Eye

disc  := wfN chars |- <?^/src/kay ?^/src/ess ?^/src/eye>@40
held  := wfN chars |- <?^/src/ess ?^/src/kay ?^/src/eye>@50
\end{lstlisting}

programs return is given in Table~\ref{tab:chars}, and two of the rows
are the point.

the program mentions it, but a redex like any other, performed only
where the reduction order demands a value.  This is the call-by-name
discipline of \S\ref{sec:language} reaching the namespace, and it is
the same phenomenon as the \texttt{K\,I\,Err} row of

expands to a chain of \texttt{EQ5} comparisons tried in order.  Reading
the first, second and third fact of \texttt{chars} takes 16{,}150,

the small variation between probes is the differing size of the segment
constructors' own encodings.  A namespace literal is therefore an
association list and should be read as one: it is the declaration that
is cheap, not the lookup.

This is a stage of a parser and not a parser.  What the table supplies
is resolution, from a name to the term it denotes.  Tokenization is the
other half, and it needs the source to be a datum the program can case
on rather than a path it can only match; that is the standard subject
of \S\ref{sec:language}, and it is unbuilt.

\section{Boundary soundness}\label{sec:boundary}

Proposition 3.1 is a statement about terms rather than programs.  What
a language owes its users is a statement about programs, and the honest
one is weaker than the theorem might suggest.  A program may not ask the
calculus for reification of code as data, and the surface has positions
where such a request could be written.  Four of them are checked by the
data rule:
\begin{enumerate}[nosep]
  \item  An operand of equality.
  \item  The argument of a quotation.
  \item  A key of a namespace literal.
  \item  A scry path.
\end{enumerate}
A quotation's body is checked by the two symbol tables instead, and a
case scrutinee and an axis pick are datum positions guarded by their own
rules, so the list above is the reach of one check rather than an
exhaustive census of the surface.

What the check establishes is one directional half of what one might
want.  At each of those positions it refuses every occupant it can
\emph{prove} to be a function: a lambda, a bare combinator, a macro, an
equation with binders, a core, a namespace literal, an under-applied
constructor.  It does not establish that an accepted occupant is a
datum.  With binders untyped, a bound variable's kind is unknown, so
\texttt{f x = EQ x <K>} with \texttt{g := f I} is accepted although
\texttt{I} is a function; catching that is the business of the second
stage.  The property is therefore ``no accepted program contains a
provable function in a data position'', not ``every data position holds
a datum'', and the two are separated by exactly the binders.

The check is a pass over the syntax tree that runs before expansion and
can only reject: it rewrites nothing.  So for every program the checker
accepts, the emitted term is the same whether the check ran or not, and
the laws of \S\ref{sec:impl} are unaffected by the presence of a type
discipline.  Note that this is erasure of the \emph{checker} and not of
the type discipline: declarations are not erased, since they drive
generation and fix continuation order.

We state this as a property the implementation enforces and tests on
every program in its corpus, rather than as a theorem with a written
proof; the formalization of the fragment is the obvious next piece of
work and is not done here.  The type discipline itself stops at this
stage.  A second stage---Hindley--Milner over the declared sum types,
so that \texttt{Suc K} is an error rather than a term---is designed
and not built, and declarations already carry the field types it would
need.

\section{Implementation and evaluation}\label{sec:impl}

An initial compiler is provided as a Python package, \texttt{skijack}.  
Its front end is two lexers over one token table and a single 
parser, so that the ASCII and Unicode surfaces are the same syntax; its 
middle is the checker of \S\ref{sec:boundary} and the generator of 
\S\ref{sec:interpreters}; its back end is macro expansion to a 
fixpoint, name resolution, lambda-lifting and bracket abstraction, each 
a total function on the tree.

Four laws are executable tests rather than remarks.  Rendering is
canonical, so $\mathit{expand} \circ \mathit{render} = \mathit{lower}$;
lifting a term against the dictionary names exact structural matches and
nothing else, so $\mathit{lower} \circ \mathit{lift} = \mathit{id}$;
checking can reject but never rewrite, so expansion is the same with it
on or off; and wherever the suite reads a value out of a compiled term
it does so behaviourally, applying the term to fresh markers and
observing which one comes back rather than inspecting combinator syntax.
The last is a discipline rather than a property of the dictionary: the
dictionary's own tests are over hashes, tie-breaks and $\mathit{lower}
\circ \mathit{lift}$, and the probing lives where values are read.  The corpus is 18 programs written in both
lexicons, and the suite is 737 tests.

Six programs fortuitiously compile term-identically to artifacts
which \citet{Davis2027} built by hand (Table~\ref{tab:programs}).
A reader may reasonably object that this is circular, since forms
generated by the compiler were designed to reproduce those terms.
The interpreter can be written out longhand, as twenty ordinary
equations, and compiled with generation switched off; it then yields the
same 618 atoms.  That establishes two things.  The generator emits
surface syntax and adds no semantics beyond the kernel fold, since the
generated and the written source compile to one term; and this
compiler's bracket abstraction agrees atom for atom, and term for
term, with the reference host's bracket abstraction over the same 
equations.  It does not establish independence from the abstraction 
algorithm, which both implementations share, nor from the equations 
themselves, which are the equations of \citet{Davis2027}.  The longhand 
source is in fact the generator's own rendered output, kept as user 
source; what it isolates is the semantics of the comparison, not its 
provenance.

\section{The virtual machine}\label{sec:runtime}

The reference reducer is an oracle, but the language intends to be
used and thus wants an implementation.  Unusually, what that implementation must  be is fixed by a theorem rather than
\emph{de gustibus}.  The two
operations the calculus cannot perform for itself are quoting a live 
term and recognizing one's structure; the first thus belongs to the 
compiler, which has the syntax tree and quotes at compile time, and the 
second belongs to the virtual machine, which holds the term on its tape 
and may factorise it freely \citep{JayGivenWilson2011}.  Matching a 
compiled subterm against a table of known terms and running native code 
for it (a jet) is therefore not an optimization of something the 
language has, but the only place the operation exists.

The recognition of a fixed set of combinators for native execution
follows Turner's extended combinator set and SKIM's microcode
\citep{Turner1979,ClarkeEtAl1980,StoyeClarkeNorman1984}, and a graph
reducer with sharing is of the same vintage.  The theorem enforces
one hard restriction: a jet may never quote on behalf of a running 
term, because the language guarantees to its users that nothing can.

Two properties of such a runtime bear on the claims made here, and both
cut against convenience.  Jets change contraction counts, so a jetted
run cannot be compared with the counts of \citet{Davis2027} at all.  And
a reducer that updates a redex in place shares work the reference
reducer repeats, which lowers those counts even with no jets installed;
the paper's numbers are the reference's substitution semantics, and an
implementation that wishes to reproduce them must decline to share.
Values are unaffected either way.  %A runtime is being built on these
%terms.

\section{Limitations}\label{sec:limits}

SKIjack has evaluation of encoded terms, including terms built at
run time.  However, even with \texttt{eval}, it lacks
\emph{reification} of a live value, for reasons discussed in
\S\ref{sec:design-principles}.

The line is visible in the compiler, and it does not fall where a
reader coming from a homoiconic language expects.  Writing an encoding
down is ordinary, and so is naming one.  Given the definition
\texttt{k2 = K K}, the program \texttt{whnfF |- <k2>@10} compiles
without complaint, at 741 atoms; so does \texttt{whnfF |- <I K>@10}, at
739.  In both the compiler knows before anything runs which term the
quotation contains, and emits its encoding.

The same quotation over a parameter does not compile:
\begin{quote}
\ttfamily f x = <x>
\end{quote}
\noindent
Stage A refuses it, reporting that \texttt{x} ``names neither table: it
is not a constructor of the object type \texttt{term} and not a level-0
name''.  The refusal is worth reading carefully, because it is not
about the value.  Had \texttt{f} been applied to \texttt{k2}, the datum
the program is asking for is precisely the one \texttt{<k2>} already
emits; the compiler can write that encoding, and does, two lines
earlier.  What differs is \emph{when} the term is known.  A level-0
name is resolved before anything runs, so quoting it is a compile-time
lookup; a parameter is bound while something runs, and recovering a
term from the value it has been given is the operation the calculus
does not have.

This is the sense in which the missing operation is \emph{reify} rather
than \emph{eval}.  Evaluation is available and needs no special
support: an interpreter is an ordinary term, and applying it to a datum
is an ordinary application, which is the whole of \citet{Davis2027}'s
tower.  Reification would have to run the other way, from a live value
to a datum describing it, and Proposition~3.1 denies any closed term
that does so for every argument.  SKIjack therefore does not forbid
reification so much as decline to pretend it has it: quotation is a
compile-time construct, the checker of \S\ref{sec:boundary} refuses the
occupants it can prove to be functions, and what remains is a language
in which the staging line is visible in the syntax rather than
discovered at run time.

The language is not self-hosting, which capability is not currently a 
design criterion for SKIjack.  This would
be a smaller undertaking than it may sound---the expander's input is a
syntax tree, which is Scott-encodable like any other datum, so the
expander is separable from the parser and text handling could stay where
it is.  What is foregone by declining is the
Futamura projections \citep{Futamura1971,JonesGomardSestoft1993} inside
the calculus: an expander that is a term
could be run under an interpreter and specialized, and the tower would
gain a level with new content rather than another copy of the same
interpreter.  Nothing else here
depends on it, and the compiler is metalevel by theorem in any case
(\S\ref{sec:boundary}), so self-hosting would relocate quotation rather
than remove it.

The type discipline stops at the stage described in
\S\ref{sec:boundary}.  The standard subject of \S\ref{sec:language} is
specified but unbuilt at time of submission, so library names are inlined and level-1 programs
do not share a quoted library.  Qualified names parse and do not yet
resolve.

While the language is Turing-complete, certain functions are 
transferred to the virtual machine host, such as scaffolding the 
initial evaluation, preserving the state and memory arena, and 
providing the supercombinator jet acceleration table.

\section{Conclusion}

SKIjack is a language whose feature set was read off an existing 
artifact rather than designed in advance, like the assembly language of 
old.  Three consequences follow from that discipline.  The declaration
of an object language generates the furniture an interpreter over it 
requires, so authoring the semantics of a new symbol is an edit to a 
single equation: the two interpreters of \S\ref{sec:interpreters} differ in 
one line and in three atoms. The generation costs nothing over manual 
construction; six programs compile to the artifacts of
\citet{Davis2027} atom for atom.
Finally, a namespace is an ordinary core parameter rather than a 
primitive, which is what makes its cost legible: a literal is an 
association list, and a hit is linear in where the fact sits.  (One 
could countenance optimizing this with a more sophisticated 
data structure.)

This is not, of course, performant!  The reference host is an oracle; 
what a runtime would do with these terms is \S\ref{sec:runtime} 
and, in earnest, other work. The standard subject of
\S\ref{sec:standard-subject} is specified and unbuilt, and with it the 
tokenization half of \S\ref{sec:chars}. Self-hosting is declined deliberately at the current time, per \S\ref{sec:limits}.
Rather, the exploration
of supercombinator techniques by \mbox{SKIjack} and its virtual machine(s)
may spur further reflection and development in the field of efficient 
functional language implementation, as well as reconceptualization of
the role of combinatory logic in the foundations of computer science
and verifiable computing.

declaration and an equation, and are invisible inside brackets, a case

\begin{lstlisting}[frame=none,
                   label=lst:grammar,
                   float=tb,
                   caption={The grammar of the SKIjack language.},
                   basicstyle=\ttfamily\footnotesize]
decl      := type-decl | sig | equation | macro | core | def | run
run       := NAME ':=' [expr '|-'] '<' expr '>' ('@' NUMBER | '@[]')
type-decl := NAME '===' ctor ('|' ctor)*
ctor      := CNAME TYPE*                     -- CNAME capitalized; fields are types
sig       := NAME ':' TYPE ('->' TYPE)*       -- optional; ignored by the expander
equation  := NAME NAME* '=' expr             -- inside a core, or at top level
core      := NAME NAME* ':=' '{' equation* '}'   -- parameters after the name
macro     := NAME NAME* ':=*' expr | NAME NAME* ':=!' expr
def       := NAME ':=' expr
expr      := app
app       := atom+                           -- left-associative
atom      := NAME | GLYPH | '(' expr ')'
           | '[' expr expr+ ']'              -- cell
           | '<' expr '>'                    -- quotation: a datum
           | '?^' atom                       -- scry
           | NUMBER '@' atom                 -- axis pick
           | '\' NAME '.' expr
           | expr '|>' '{' branch (';' branch)* '}'
           | 'ns{' fact (',' fact)* '}'
branch    := CNAME NAME* expr
fact      := path '=>' expr
path      := ('/' NAME)+
\end{lstlisting}
